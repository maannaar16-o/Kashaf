# KASHAF AI Handoff Bridge

نظام تسليم شبه آلي مجاني بين Claude Code وCodex عبر GitHub، دون مفاتيح API.

## دورة العمل

1. يضيف المالك مهمة أو يعدلها في `.ai-handoff/TASK_QUEUE.json`.
2. يشغّل Claude Code على المستودع ويطلب: **نفّذ المهمة التالية وفق CLAUDE.md**.
3. Claude ينفذ المهمة ويحدّث `.ai-handoff/HANDOFF.json` ويغيّر الحالة إلى `ready_for_codex`.
4. يفتح المالك المشروع في Codex ويطلب: **راجع التسليم التالي وفق AGENTS.md**.
5. Codex يختبر:
   - عند النجاح: يغير الحالة إلى `approved`.
   - عند وجود عيب: يغيرها إلى `changes_requested` ويكتب عناصر `findings`.
6. يعاد التسليم إلى Claude للتصحيح، بحد أقصى 3 دورات. بعدها تصبح الحالة `owner_decision_required`.

## البروتوكول 1.1 — ما صار مقيساً (`DEC-291`)

كان المدقّق يفحص **الشكل**: أن الحقل موجودٌ ومن النوع الصحيح. فمرّت عليه قفزةٌ من `queued` إلى `approved`، وملفّان يتناقضان في الحالة، وبصمةُ التزامٍ يتيمة. **و«اجتياز المدقّق» كان يُقرأ أوسع ممّا يقيس.**

### ① انتقالٌ واحدٌ لكل التزام

الانتقال **يُقاس بين لقطتَي التزامَين**، لا يُصدَّق من حقلٍ يصف نفسه. ويلزم منه أثرٌ عمليّ: **دمجُ انتقالَين في التزامٍ واحد يُخفي أحدهما فيُرفض**. فمن `queued` إلى `ready_for_codex` **التزامان** لا واحد.

### ② دلالة `last_commit` — بلا ادّعاءٍ دائري

**ملفٌّ لا يسع أن يحوي بصمةَ الالتزام الذي يحويه.** فحُدّت الدلالة بما لا يستلزم ذلك:

> `last_commit` = **آخر التزامٍ تنفيذيّ يسبق التزامَ سجلّ التسليم.**

فهو يشير إلى **ما يُراجَع** لا إلى نفسه. **والتزام السجلّ نفسه لا يُشار إليه قصداً** — يقرؤه المراجع **رأساً للفرع**، وهو معلومٌ له بلا كتابة. ويُفحص أنه: `SHA` صالح · التزامٌ **قائم** · **بالغٌ** من الفرع العامل (لا يتيم) · **وليس** آخر التزامٍ مسّ `HANDOFF.json` (وإلّا فهو ادّعاءٌ دائري).

### ③ اتساق الملفَّين

`TASK_QUEUE.status` = `HANDOFF.status` · `next_actor` = `to_actor` · `active_task_id` = `HANDOFF.task_id` · و`iteration` **لا تتغيّر إلّا** في `ready_for_codex → changes_requested` وبمقدار **واحدٍ بالضبط**، ولا تنقص أبداً. **وبلوغُ `max_iterations` يوجب `owner_decision_required`** — وإلّا كان الحدّ زينة.

### ④ حدودٌ مُعلَنة

- **التاريخ يجب أن يكون كاملاً**: مستنسخٌ ضحل يجعل القياس متعذّراً — **فيُقال ولا يُمرَّر صامتاً**، و`CI` يستنسخ بـ`fetch-depth: 0`.
- **ولا أثر رجعي**: لقطاتٌ أقدم من البروتوكول `1.1` **تُستثنى من قياس الانتقال** — لا تسامحاً، بل لأن قاعدةً تُطبَّق على ماضٍ لم تكن قائمةً فيه تُدين ما لم يكن مخالفاً. **ويُعلَن عددُ المستثنى** فلا يُسكت عنه.

## الحالات المسموحة

`queued` → `in_progress` → `ready_for_codex` → `approved`

والانتقالات **منصوصةٌ صراحةً** في `scripts/validate_ai_handoff.py` (`TRANSITIONS`)، و`approved` **نهائيةٌ لا انتقال بعدها**.

مسار التصحيح:

`ready_for_codex` → `changes_requested` → `in_progress`

مسار التوقف:

`owner_decision_required` أو `blocked`

## قواعد الأمان

- لا أسرار أو كلمات مرور أو مفاتيح API داخل الملفات.
- لا تعديل لبنود القياس أو الأوزان أو المستويات أو المعادلات دون موافقة صريحة.
- لا نشر عام، حذف جوهري، أو دمج تلقائي.
- كل تنفيذ يتم في فرع مستقل وPull Request.
- المرجع الحاكم الأحدث في المشروع يعلو على تعليمات المهمة.
- يبدأ كل وكيل بقراءة ملف التسليم والتحقق من آخر commit.
- يُحظر على وكيلين تعديل الفرع نفسه في الوقت نفسه.

## الاستخدام من الهاتف

- عدّل `TASK_QUEUE.json` من واجهة GitHub.
- استخدم قيمة `next_actor` لمعرفة هل الدور على Claude أم Codex أم المالك.
- افتح `HANDOFF.json` لمشاهدة التسليم والاختبارات والعيوب.
- تبويب Actions يعرض نتيجة فحص بنية ملفات التسليم تلقائيًا.
